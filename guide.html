⭐ The Lite version (start here if the robot crashes)

If the micro:bit shows a sad face and disconnects, use the Lite version: lite.html on the phone and move-motor-lite.ts on the micro:bit. You need both, because the crash happens on the micro:bit, not the phone.

Why the full version can crash: the motors and ZIP LEDs use NeoPixel-style chips. Sending to them briefly stops the micro:bit listening to anything else, including the Bluetooth radio. Do that too often and Bluetooth faults, so the micro:bit crashes (sad face) and restarts. The full version refreshed the lights every 0.4 s and the motors many times a second.
What the Lite micro:bit code does differently: it only sends to the motors when the speed changes, only sends to the lights when you switch them on or off, plays one sound at a time from a single loop, sends the distance only when it changes by 2 cm (or every 0.5 s), and keeps the Bluetooth message handler short. Smart modes show as one dot on the bottom row of the display instead of a number.
In LiteLeft out (for now)
Joystick & tilt · horn · steady headlights · auto-stop · parking beeps · distance graph · follow me · explore · blocks · draw a path · record & replay · lap timer & clapIndicators & hazards · reversing beep · light shows · dances · line follow · radar · gesture & voice
🧪 Engineering habit: once Lite runs reliably, add back one feature at a time and test after each. If it crashes, you know exactly what caused it. This is incremental development.

1. Upgrading from the first version

  1. micro:bit: open your MakeCode project, switch to JavaScript view, delete everything and paste in the new move-motor-bluetooth.ts. The extension (only bluetooth) and the No Pairing Required setting stay the same. Download it to the micro:bit.
  2. Website: in your GitHub repository, click Add file → Upload files. Upload the new index.html and guide.html together. Uploading a file with the same name replaces the old one. Click Commit changes.
  3. Wait about a minute for GitHub Pages to rebuild, then refresh the page on your phone. If you still see the old version, close the tab and open it again. Phones keep a saved copy for a short while.
  4. Tap Try demo mode first. A pretend robot lets you try every tab without the real one.
💡 The micro:bit shows a number when its mode changes: 0 = manual, 1 = follow me, 2 = explore, 3 = line follow. It's a handy way to check that it received the message.

2. The big idea: who does what?

There are two computers working together: the micro:bit on the robot and the phone. They talk over Bluetooth, but each message takes roughly 20–100 ms to arrive, and sometimes longer. That delay decides where each job runs.

Computing concept – distributed systems and latency. If line following ran on the phone, the robot would read the sensor, send it to the phone, wait for the decision and then steer. By then it has already driven off the line. Putting the fast loop on the robot avoids the round trip.

3. The messages (our protocol)

A protocol is an agreed set of rules for communicating. Ours is deliberately simple: one short text line per message. The first letter says what the message is; the rest holds the values.

4. Drive tab

🕹️ Joystick and 📱 Tilt phone

How it works
The joystick gives an x (left/right) and y (forward/back) value from −1 to 1. Two equations mix them into motor speeds: left = y + x, right = y − x. Push straight up and both motors go forward. Push right and the left motor speeds up while the right one slows down, so the robot turns right.
Concept: a heartbeat. The phone re-sends the current command 6 times a second. If the micro:bit hears nothing for 0.7 s it stops. That is a failsafe: losing the connection makes the robot stop, never run away.

💡 Lights, indicators, hazards, reversing beep micro:bit

The 4 ZIP LEDs act as headlights (front, white), tail lights (rear, red, brighter when stopped, like brake lights) and amber indicators. A second forever loop on the micro:bit flashes them every 0.4 s and beeps while both motors run backwards.
Auto-indicate watches the motor speeds. If one side is more than 25 % faster than the other, the robot is turning, so the matching indicator comes on.
Concept: selection (if left is slower than right, indicate left) and concurrency: two loops run "at the same time" by taking turns.
🔧 If the lights appear in the wrong corners, change the four numbers LED_FRONT_LEFT etc. near the top of the micro:bit code.

🅿️ Parking beeps phone

Below 60 cm the phone beeps. The closer the obstacle, the shorter the gap between beeps. Under 8 cm the beep is almost continuous and higher pitched, like a real car.
Concept: a linear mapping. 5 cm → 60 ms gap, 60 cm → 700 ms gap, with values in between scaled proportionally: gap = 60 + (distance − 5) ÷ 55 × 640.

⏺️ Record & replay phone

While recording, every new command is stored with a timestamp (ms since you pressed Record). Repeated heartbeat copies are ignored. Replay waits the same amount of time between each command. The route is saved on the phone, so it is still there after you refresh.
Concept: data structures. The recording is a list of records such as {t: 1520, c: "D60,60"}.
🤔 Discuss: why does the replay never end up in exactly the same place? (Wheel slip, battery level, Bluetooth delay. The robot has no way to measure where it actually is. That is open-loop control.)

5. Smart tab (all run on the micro:bit)

Each smart mode is a sense → decide → act loop that runs about 15 times a second. The phone sends P every 0.4 s. If the robot hears nothing for 1.5 s it switches itself back to manual and stops.

🚶 Follow me

if distance > 70:            stop            # lost you
elif distance < gap - 5:     reverse         # too close
elif distance > gap + 5:     forward, faster the further away you are
else:                        stop            # just right
Use: hold a large book flat in front of the sensor at about 20 cm and walk slowly backwards. Smooth, flat objects reflect sound best; a hand works but less reliably.
Concept: feedback / proportional control. Speed = (distance − gap) × 3, so the further the robot falls behind, the harder it tries to catch up. The ±5 cm zone (a dead band) stops it jittering back and forth.
📍 Why not follow the phone's GPS? Phone GPS is only accurate to about 5–10 m, which is bigger than a classroom, and Bluetooth signal strength jumps around too much to measure distance. The ultrasonic sensor is accurate to about 1 cm.

🧭 Explore (obstacle avoidance)

Drives forward. When something is closer than 25 cm it stops, reverses for 0.35 s, turns a random direction for a random time, and carries on.
Concept: randomness makes it less likely to get stuck going back and forth in a corner. This is how early robot vacuum cleaners worked.
🧪 Challenge: build a maze from books. How long does Explore take to escape? Could a smarter rule (e.g. "always turn right", the wall-follower algorithm) do better?

〰️ Line follow

Two sensors underneath shine infrared light at the floor and measure how much bounces back (0–1023). A dark line reflects less than a light floor. 
difference = left - right
if difference > dead band:     turn left
elif difference < -dead band:  turn right
else:                          go straight
Set-up:
  1. Make a loop with 2 cm black electrical tape on a light floor (gentle curves at first).
  2. With both sensors over plain floor, tap Suggest dead band. Sensors are never perfectly matched, and this ignores the normal difference between them.
  3. Place the line between the sensors and press Start. If it immediately steers off the line, tap Flip steering.
Concept: calibration and thresholds. Watch the live bars move as you slide paper under the robot; that is the raw data the algorithm decides from.

6. Sensors tab

📏 How the ultrasonic sensor measures distance

The micro:bit sends a 10 µs pulse to the trigger pin (P13). The sensor sends out a burst of 40 kHz sound (too high to hear) and the echo pin (P14) stays high until the echo returns. Sound travels about 343 m/s, so it takes about 58 µs to go 1 cm and back: distance = echo time ÷ 58. The code uses 39 on the older micro:bit V1 because its timer counts differently.

📈 Live distance graph phone

Plots the last 15 seconds of readings. Gaps mean "nothing in range". Dashed lines show the 12 cm auto-stop and 30 cm caution levels.
🧪 Investigate: point the robot at a cushion, then at a wall. Which gives a steadier line? Why? (Soft surfaces absorb sound; angled surfaces bounce it away.)

📡 Radar scan phone

The robot turns a small step, stops, waits for a fresh reading and records (angle, distance), repeating until it has turned 360°. Each pair is turned into a dot using trigonometry: x = sin(angle) × distance, y = cos(angle) × distance. Calibrate first: tap Test 1 step several times and adjust the slider until the number matches how far it really turns.
Concept: polar → Cartesian coordinates, and how robot vacuums and self-driving cars (LiDAR) build a map of a room.

7. Program tab

📏 Calibrate first!

The robot has no wheel sensors, so it can't measure distance travelled. Instead the app converts distance into time: time = distance ÷ speed. Measure the speed once:
  1. Tap Drive 2 s. Measure how far it went with a ruler. If it went 46 cm, type 23 (cm per second).
  2. Tap Spin 2 s. Estimate the angle. One and a quarter turns = 450°, so type 225 (degrees per second).

🧩 Blocks

Tap blocks to build a program, edit the numbers, and use ▲ to move a block up. The same program appears as Python underneath, which makes a good bridge from blocks to text code. Repeat … End repeat makes a loop; the app "unrolls" it into a list of steps before running. Until wall keeps driving while the distance is bigger than your number.
Concepts: sequence (blocks run in order), iteration (count-controlled for = Repeat; condition-controlled while = Until wall), and selection inside the robot's safety checks. The orange outline shows which block is running: a simple trace.
🧪 Challenges: (1) Drive a square and come back to the start. (2) Drive a triangle: what angle do you need? (120°, not 60°!) (3) Drive to a wall, turn round and come back.

✏️ Draw a path

Draw with your finger from the ▲. Each grid square is 20 cm. The app takes a point every 12 cm, then for each line segment works out:
  1. the heading it needs, using atan2;
  2. the turn = new heading − current heading (kept between −180° and 180° so it never turns the long way round);
  3. the length = Pythagoras, √(dx² + dy²).
Short turns under 8° are ignored and straight bits are merged, so the robot doesn't stutter.
Concept: abstraction: a wobbly finger line becomes a simple list of "turn, drive" instructions. This is like the way a sat-nav turns a road into directions.

8. AI tab

✋ Gesture driving phone

Uses Google's MediaPipe Hand Landmarker, the same tool as our crossing project. A trained neural network finds 21 points (landmarks) on your hand in every camera frame. The app then uses simple maths on those points:
  • Steering: where the middle of your palm (point 9) is compared with the centre of the picture gives x and y, just like the joystick. The white box is a dead zone.
  • Fist = stop: if 3 or more fingertips are closer to the wrist than their knuckles are, the fingers are folded.
  • No hand seen = stop. This is a safety rule.
Start the camera, check the dots follow your hand, then turn Drive with hand ON.
Concept: the AI does the hard part (recognition); ordinary rules turn its output into decisions. Most real AI systems are built this way.

🎙️ Voice control phone

The browser's speech recognition turns speech into text. The app then searches the text for keywords, so "please go forward" still works. "Forward" drives 40 cm, "left/right" turns 90°, "stop" stops everything.
Concept: string searching. The order of the checks matters: "go back" contains "go" (forward!), so "back" is checked first. Ask students to find other words that could confuse it (e.g. "write" sounds like "right").

9. Fun tab

💃 Dances & 🌈 light shows

A dance is just a list of steps (drive, spin, note, lights), so it uses exactly the same runner as block programs. Students can design their own in the Blocks tab using Note and Light show blocks.

⏱️ Lap timer, obstacle course and 👏 clap to start

Set out a course with cones or cups. Tap Start (or turn on Clap to start and clap), tap Lap each time the robot crosses the line, and tap +2 s when it knocks something. Finish, type a name and Save for the top-5 leaderboard (stored on that phone).
Clap detection listens to the microphone. A clap is a short, very loud spike, so it triggers when the loudest sample is over a threshold and 5× louder than the running average of background noise. A loud classroom raises the average, so steady talking doesn't set it off.
Concept: signal processing and avoiding false positives; sorting a leaderboard.

11. Safety rules

  • STOP EVERYTHING is always at the bottom of the screen. It cancels programs, smart modes and gesture driving.
  • The robot stops if: Bluetooth disconnects · no drive command for 0.7 s · no ping for 1.5 s in a smart mode · the app is hidden or the phone locks · something is closer than 12 cm while driving forward (auto-stop).
  • Drive on the floor, never on tables. Keep fingers and hair away from the wheels.
  • Only one phone can connect to a robot at a time. Label robots so students connect to the right one.
